RUNTIME-TESTED (in a GML simulator, real hub code, mocked game engine)
  - Attack sweep with the merged code (build 17, gmlsim, trio party): every attack of every phase/turn for Normal, Elec, Violet,
    Thorn and Cyan, plus Kaizo's named attacks and Kaizo Side B's phase/turn list, was started and run until its turn ended
    (turn timer reached 0). Results: all end normally; the only runs not seen to the end are the Knight's final roar/kill
    attacks (they run longer than my time limit by design) and a few Cyan attacks that the simulator cannot finish (missing
    sound/asset values in the simulator, not in the game). Smaller samples were run with solo Kris, solo Susie-less/Ralsei,
    Noelle + Susie, three Kris, and Kaizo Side B with solo Kris and a no-Kris party (see "Party samples").
  - THE KAIZO "ATTACK JUST STOPPED" FREEZE: root cause found and fixed. The Kaizo mod stores object numbers from its own data
    file (e.g. 672 for Rotating Slash). The merge turned these numbers into the base game's numbers, so Kaizo's combo attacks
    (Frenzy, Multislash, ...) spawned the plain base Rotating Slash, which does nothing in Kaizo, and the turn never finished.
    The merge now converts such numbers into the right per-knight objects (113 spots). Verified in the simulator: the same
    attacks now end. The same bug also made some Kaizo/Violet/Cyan attacks use base-game artwork; also fixed.
  - Violet Weird Route scenes (simulator, scene code with dialogue/animation objects mocked): the loss of Ralsei, then Susie, then Kris's
    X-Slash finisher for [Kris,Susie,Ralsei], [Kris,Susie,Noelle], [Kris,Noelle,Ralsei], [Ralsei,Susie,Kris], three Kris, Kris solo,
    Kris+Susie, Kris+Ralsei, Kris+Noelle: all reach the end of the scripted sequence, X-Slash unlocked, no errors.
  - Elec practice (simulator): attack picker (left/right, wraps), picked phase/turn forced, Knight HP and party HP held, all 21
    pickable attacks run to the end of their turn.
  - Kaizo final attack (Roaring Delta): ran 1092 frames in the simulator with no error; its end (shatter + kill) could not be simulated. In a hub run the kill now reports a normal defeat instead of jumping to the failure room (compiled only).
  - Party samples (simulator, attacks to end of turn, no errors): solo Kris, solo Ralsei, Noelle+Susie, three Kris for Normal/Violet/Thorn; Elec solo Kris and three Kris; Kaizo Side B solo Kris and Susie+Ralsei; Violet Side B with Noelle (partly inconclusive: time limit).

    independently (fixed: animation state was shared per character; simulator-tested only).
  - Practice mode exists for Kaizo Knight and Elecknight (the Elec one is added by this hub, not part of the mod); no attack slow-down.
  - Weird Route (Kaizo Side B, Violet) needs Kris in the party. Without Kris it is switched off with a message.
  - With a full party of duplicates the invisible stand-in objects can pick slot 0.
  - No Healing: heal popups may still show; scripted HP changes inside a knight's fight code are not blocked.
  - Some hit sources may bypass the game's damage routine and so not trigger No-Hit.
  - Cyan Knight is a joke fight: excluded from Rush, Random, No-Hit and records.

BUILD 44 (on top of 43)
 - THE CRASH YOU REPORTED (build 43, as soon as you reached the Knight Hub):
     ERROR in action number 1 of Step Event0 for object obj_knight_ctrl:
     Variable <unknown_object>.lq(116352, -2147483648) not set before reading it.
     at gml_Script_kfo_local_run
   Why: the online code kept its state in a global variable called kfo, and it also had a function called kfo().
   GameMaker makes every script function a global variable of the same name, so global.kfo was the function, not the
   state, and the first online check of every frame read a field of the function. The function is now kfo_get(), and
   nothing in the online code shares a name with a function any more.
   Why the tests missed it: the simulator kept functions and global variables apart. In the real game such a variable
   silently IS the function, so the simulator now stops with an error whenever a global variable has a function's name.
   The hub's lint and the data.win check look for it too: on the build 43 data.win the new check finds exactly one such
   name in the whole game (kfo), on build 44 none.

   * network_create_socket / buffer_create give a plain number in older GameMaker runtimes and a typed handle in newer

     The network test now runs three ways: numbers, handles, and handles with plain-number socket ids in the Async

   * id is one of GameMaker's built-in (read-only) variable names. The game's own player records and messages now use

WHAT CHANGED
1. DRBR-Setup.exe (new). It finds DELTARUNE by itself, through Steam's registry entry, every Steam library in
   libraryfolders.vdf, the app manifest (appid 1671210) and the usual folders, or a folder picked with Browse.
   - It checks that the vanilla Chapter 3 data.win is the supported build (SHA-256). With the older Knight Hub in Steam's
     folder, it checks the Knight Hub's own clean backup (data.win.vanilla) instead and leaves Steam's copy alone.
   - It installs DRBR as its own copy of the game in %LOCALAPPDATA%\DRBR: DELTARUNE.exe, Chapter 3's sounds, language,
     videos and options, the music, DRBR's data.win built from the vanilla one plus the patch, the multiplayer files,
     the songs, the provided starting save, DRBR Launcher and DRBR Updater.
   - It adds the shortcuts and an Apps & features entry (per user, no admin).
   - Steam's DELTARUNE folder is only read.
   - The install is one transaction: build in staging, switch with one rename, verify, roll everything back if any step
     fails. A transaction interrupted by a crash or power loss is undone at the next start.
   - Silent mode (/S) and a result file are for testers.
2. DRBR Launcher (new). PLAY, CHECK FOR UPDATES, REPAIR INSTALLATION, RESTORE STARTING SAVE, SETTINGS (start mode, update
   check at start, uninstall), RELEASE NOTES, OPEN INSTALLATION FOLDER.
   - PLAY first checks the install, the starting save and the profile, and offers a repair when something is damaged.
   - After the game starts, it reports the room the game reached ("DRBR started in room_dw_snow_zone - the room before
     the Roaring Knight").
   - After the game closes, it says whether the player's own DELTARUNE saves changed (they are hashed before and after).
3. Updates. The launcher reads update-manifest.json from the latest GitHub release. It accepts it only with a valid
   signature: RSA-3072, SHA-256, with the public key built into the launcher.
   - It downloads only the files whose SHA-256 it does not have, resumes stopped downloads (HTTP Range), and checks
     every file.
   - It installs with the same transaction as the Setup.
   - The launcher replaces itself through DRBR Updater, which checks the new file's SHA-256 and keeps the old one until
     then.
   - No background service, no token in any program.
   - Update checks are switched OFF in this build: there is no GitHub repository yet.
4. THE STARTING SAVE (game, DRBR mode). The DRBR install has drbr_data\drbr_profile.cfg next to its data.win. With it,
   the game skips the intro and the file menu.
   - It checks the provided save (drbr_data\start_filech3: size and SHA-1), copies it byte for byte to
     %LOCALAPPDATA%\DELTARUNE\drbr_profile\filech3_0, and loads it as the file menu's CONTINUE does. The result: Chapter
     3, story point 320, room_dw_snow_zone, Kris / Susie / Ralsei, right before the Roaring Knight.
   - Every story file (filechN_M, dr.ini, keyconfig_N.ini, config_N.ini) lives in drbr_profile\. The player's own saves
     are never read or written.
   - The game writes a start report (drbr_profile\last_start.ini) for the launcher.
   - A chapter switch or the chapter select restarts DRBR at its start.
   - A damaged or unknown starting save stops the start with a message (REPAIR) and loads and writes nothing.
   - Start mode "continue" (Launcher > Settings) keeps a valid DRBR save, and otherwise falls back to the provided save.
   - The mod's own settings (knight_hub.ini, knightfights_online.ini) are shared on purpose, so skins, SOUL colours,
     names and keybinds persist across updates, repairs and reinstalls.
5. A ROOM WITH A NEWER DRBR (game + launcher).
   - The game writes the room down (drbr_profile\pending_join.ini) and says to update with DRBR Launcher.
   - The launcher then offers the update.
   - The updated game offers that room again: "DRBR IS UPDATED - Join the room you tried to join before the update?",
     JOIN / NOT NOW. It never joins by itself.
   - A note older than an hour is dropped.
6. THE NAME (game, DRBR mode). In the DRBR install the game says DRBR in these places:
   - the build stamp on every page of the sign's menu: "DRBR - BUILD 51 - <time>"
   - the credits page
   - the messages about a room or host with another build ("... a newer DRBR. Close the game and update it in DRBR
     Launcher.")
   - the missing kf_steam.dll messages (DRBR Launcher > Repair instead of PLAY_KNIGHT_HUB.bat)
   - the newer-preset notes
   - the "no hub sign with this save" note
   Without the cfg (the in-place Knight Hub), every text is word for word as before.
7. THE REPOSITORY (new): drbr.json (versions, GitHub repository, public key, supported game build, save profile), the
   programs' source, the provided save, packaging and signing tools, scripts, CI and release workflows, and the docs:
   README, INSTALLATION, SAVE_SYSTEM, UPDATING, RELEASING, DEVELOPMENT, TROUBLESHOOTING, ARCHITECTURE and CHANGELOG.
   - The private signing key, DELTARUNE's files, decompiled game code and anyone's saves are excluded (.gitignore, plus a
     CI check).
   - The game patch is made only on the author's machine, never on a GitHub runner.
